Home uses the authenticated `GET /api/v1/user/home` contract. Identity and XP load independently through the existing `/user/profile?summary=true` endpoint, without the legacy curriculum/full-history stats scan. Profile drill-down keeps its original detailed response.

The Home read path uses four indexed projection reads and one latest active/paused lesson lookup with related metadata. Results share a repeatable-read snapshot. The daily range is bounded to 28 IST dates; lifetime results contain at most four difficulty buckets. No cache or raw-history reconstruction is used on Home loads. The latest completed PvP result is a maintained snapshot; the product has no rating model, so Home presents no invented rating/tier.

Canonical data and definitions:
- Submissions: persisted lesson question attempts and explicitly selected answers from practice, Daily Challenge and PvP. Retries and replays count separately. `TIMEOUT` and null selections in timed modes do not count. An abandoned session's already submitted answers count. These are correct **answers**, not unique problems solved.
- Accuracy: correct submissions / all submissions. An empty denominator returns null.
- Average correct time: positive recorded response times on correct regular practice, Daily Challenge and non-late PvP submissions. Untimed replays, lesson answers, incorrect answers, timeouts and missing timing are excluded. Hinted answers remain included. Timing is recorded by existing clients; it is not a verified competitive speed score or session duration.
- Activity: submissions grouped by their stored submission timestamps. Prisma timestamps are stored as UTC; conversion explicitly interprets UTC before applying Asia/Kolkata. Auto timeouts/app opens/session launches do not light up the calendar.
- Streak: the existing Daily Challenge rule (all required answers correct, midnight IST). It is labelled separately from learning activity. Best streak comes from existing `highestStreak`.
- Achievements: first submitted answer, 25 correct answers, 10 hard correct answers. Stable backend IDs and persistent `(user_id,badge_id)` keys prevent repeat awards. Existing reliable submissions qualify during backfill. No historical award date is invented. Awards remain earned after later record corrections; current progress is derived from counters.

Persistence is database-owned: source-table triggers synchronize a `(source,source_id)` projection ledger; ledger changes reverse old counters and apply new counters atomically to totals and day rows. A per-user transactional advisory lock serializes difficulty buckets and badge thresholds. Source unique constraints plus ledger primary keys make repeated operations safe. Deleting a submission subtracts its counters; deleting a user cascades cleanly. Questions' difficulty is captured at submission synchronization; later curriculum edits do not silently rewrite historical results. Unknown inline difficulty stays UNKNOWN. Match completion maintains the latest PvP result.

Deployment: apply `20261013_home_rollups` through the authorized migration process **before** deploying the API/client. The migration locks the source answer/match tables for its set-based historical import and runs in a transaction, so schedule a write maintenance window sized to real history. Existing timestamps, IDs, correctness and published script-version difficulty support the backfill; unavailable lesson timing is not invented. Only retained source history is represented. This migration has been prepared, not executed in this workspace.

Validation: `npm run test:home`, backend build, Prisma schema validation and Home Flutter tests require no database. `tests/rollups.sql` exercises projection corrections, duplicate safety, real practice source writes, midnight conversion, timeout exclusion, badge uniqueness and user deletion in a rollback transaction. It requires an explicitly authorized disposable PostgreSQL database with migrations applied. Validate source adapters for every mode, concurrent writes/thresholds and query plans there before release. Local DB actions and migrations are prohibited in the current repository instructions.

Reconciliation after an authorized administrative history repair: pause source writes; compare `home_events` with `home_source_events` using `(source,source_id)` and the same UTC-to-IST conversion/filter definitions. Upsert changed/missing events and delete removed source events in one transaction; ledger triggers maintain day/totals automatically. Do not write totals/day rows independently. PvP snapshot corrections must refresh the corresponding completed match (normal finalization already does this); deleting the latest match removes its snapshot, so reconciliation must select the latest remaining completed match if needed. The migration's set-based `DISTINCT ON` query supplies that repair definition. Preserve earned badges.
