## Timing, rate and session contracts

- Daily total time is **the sum of per-question server durations**, excluding reading feedback/between-question delays. A late answer becomes an incorrect TIMEOUT, capped at its deadline; early TIMEOUT is rejected. Deadline is the earlier of the question limit and midnight IST. A previous-day unaccepted answer is rejected even if cron has not run. Accepted duplicate replies remain recoverable after completion/day rollover.
- Answer receipt is captured after the entire JSON body is received, never from client fields or header arrival. Client `responseTimeMs` is ignored for Daily scoring. The requested latency-fairness TODO is included; no leaderboard or compensation algorithm was added.
- Central fixed Redis policies: auth/refresh 120/min per IP; admin login 5/15 min per IP; session creation 30/min per learner; mutations 180/min per learner; Daily 60/min per learner; Ranked reads 60/min per learner; WS connections 120/min per trusted peer; WS messages 240/min and queue actions 6/10 sec per learner. Fixed windows may permit boundary bursts. HTTP 429 includes Retry-After. Protected operations fail closed with 503 during Redis failure; there is no local counter fallback. Ordinary unrelated GETs remain available. WS processing also bounds pending frames.
- `TRUST_PROXY` is empty by default. Configure only actual trusted proxy IPs/CIDRs; forwarded client addresses are ignored from untrusted peers.
- Existing ENV refresh expiry now controls opaque token lifetime. New targeted keys: `JWT_ISSUER`, `JWT_AUDIENCE`, `ADMIN_JWT_EXPIRATION`, `TRUST_PROXY`. The unused required `JWT_REFRESH_SECRET` was removed. Broad provider/job/body-budget operational ENV conversion remains deferred; reward formulas and centralized abuse policy constants remain code policy.
- Legacy JWTs without the new claims require refresh or login; admin requires login. Logout does not instantly revoke already-issued access tokens: they and sockets expire at the configured access deadline (default 15 minutes). Rotation deliberately has one winner; losing concurrent refresh or a lost rotation acknowledgment can require login. Flutter coalesces simultaneous refresh attempts. No token resurrection/session-family platform was introduced.
