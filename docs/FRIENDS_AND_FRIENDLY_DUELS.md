# Friends and friendly Practice duels

## App identity and future domain/Firebase setup

Android `applicationId` and Kotlin namespace, and the iOS main bundle identifier, are `com.aptiqu.app`. iOS test targets use `com.aptiqu.app.RunnerTests`. The Kotlin activity moved to the matching package directory. Website addresses are separate from store identifiers. Buying `aptiqu.in`, using `www.aptiqu.in`, or later moving to `aptiqu.com` does not require changing this app identifier. The top-level domain is not a universal store prohibition; reverse-domain code namespaces can introduce keyword/tooling issues, which this stable identifier avoids.

Before registering Firebase, confirm the identifier is available for your app in the store accounts. Firebase's Android package name cannot be changed after registration: https://firebase.google.com/docs/android/setup. Android identifier requirements: https://developer.android.com/build/configure-app-module. Apple bundle-ID guidance: https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleidentifier.

Register the Android Firebase app as `com.aptiqu.app` and the Apple Firebase app with bundle ID `com.aptiqu.app`. Obtain actual `google-services.json` and `GoogleService-Info.plist` from your own project and configure the Firebase SDK/FCM when you set up notifications. No fake Firebase project, configuration or keys are added here. Update the Google sign-in Android OAuth client to the new package and the actual debug/release signing certificate SHA fingerprints. The build still uses the existing debug signing setup; configure your release keystore before uploading to Play.

The existing `API_BASE_URL` Flutter dart-define controls the API host. When DNS/TLS and the reverse proxy are ready, rebuild using your actual HTTPS API URL, for example `--dart-define=API_BASE_URL=https://api.aptiqu.in/api/v1`. The app derives the social WSS URL from that base; no new hardcoded live domain is assumed. Proxy both `/ws/social` and `/ws/pvp` with WebSocket upgrade support. Universal/app links are not claimed or configured for an unowned/unverified domain.

## Data and state ownership

Definitions live directly in `backend/prisma/schema.prisma`. Deploy manually with `npx prisma db push`, `npx prisma generate`, and `npm run build`. No migration or schema bootstrap scripts are added. Redis and BullMQ already used by this backend provide live delivery, online presence and durable deadline jobs; PostgreSQL remains authoritative for friendship, invitation, match, answer and XP state. Do not run the old database-backed XP test script under the repository's local database restrictions; the new social tests are isolated mocks.

A friendship is one unique canonical `(low_user_id, high_user_id)` record, with pending/accepted/rejected/removed states. Participant IDs are ordered before user-row locks, avoiding opposite-direction request races. Self-invites and third-party responses are rejected. Responses carry the server version timestamp, so stale popups cannot accept a replacement request. Rejection has a 24-hour reinvite cooldown. Removing a friend preserves history, prevents new invitations and cancels pending duels; an already mutually accepted duel can finish.

Friend lists are keyset-paginated (50/page). Learner search is a normalized name-prefix lookup, keyset-paginated (20/page), supported by a `text_pattern_ops` index. Newly created and registration-completed profiles populate `search_name`. If retaining profiles created before this field existed, explicitly update their profiles or populate their search_name before relying on search; no hidden backfill runs on startup. Public profiles expose name/avatar and learning/game stats, excluding email, Google ID, birthdate, gender, religion and other private registration fields. Profile stats reuse Home's canonical aggregates rather than reconstructing attempts in Flutter.

Capacity/abuse bounds: 1,000 accepted friends, 100 sent pending friend invitations, 200 received pending friend invitations, 30 friend invitations/hour, 10 duel invitations/minute, 60 searches/profile views per minute and five live connections per account. These bounds are enforced server-side. Active friend-page presence subscriptions cover its current page only (at most 50 IDs).

Online means at least one authenticated foreground connection renewed within 60 seconds. Presence is a Redis TTL sorted set per account and works across API instances and multiple devices. Heartbeats occur every 25 seconds; a central server heartbeat loop closes stale/expired sessions. When Redis is unavailable, presence is unknown rather than a fake offline value, and invitation creation/search/profile rate limiting fail closed with a retryable error. Redis pub/sub targets only the recipient's subscribed account channels. Lost live events do not delete invitations: the app reloads its indexed inbox on connection/reconnection and foreground resume. There is no all-user polling loop or process-local authoritative duel state.

Current invitations are in-app popups. Offline friend invitations appear when the app next opens. An offline friend who does not open the app within a duel's 60-second window is reported as not responding. Firebase background push is a future transport after your actual project is configured; it is not simulated here.

## Friendly duel rules

Friendly Duel is selectable in both Random and Custom Practice, independently of Smart AI Picks and the timer. The inviter selects from accepted friends. The server rechecks friendship on creation and acceptance. Both accounts reserve a unique duel seat, preventing overlapping invitations/matches across replicas or devices; Ranked creation also checks these reservations, and a new friendly invitation rejects active Ranked participants.

Invitations expire after 60 seconds. Acceptance/rejection/cancellation use conditional database transitions; late or conflicting responses cannot create a second match. A BullMQ delayed job expires unanswered requests and releases seats, with lazy expiry checks covering missed jobs. Accepted unfinished duels have a 24-hour resource deadline. Terminal duels clear outstanding deadline jobs where possible. Cancel/accept races resolve to one database state; leaving an accepted duel abandons it without rewards.

Acceptance allocates two ordinary Practice sessions linked to the duel, each containing the same ten distinct question IDs in the same shuffled order. A single immutable deck snapshot is stored with the duel, so later admin question edits cannot change prompts, options or grading halfway through the match. Unanswered solutions remain masked by the existing Practice API. Selection is restricted to the current live curriculum and the chosen Custom scope. It does not invoke AI generation inside the match transaction. UUID range sampling avoids sorting the entire published inventory by random().

With AI Picks, five questions come from the requester's weak topics and five from the recipient's, using retained Practice, lesson, Daily Challenge and Ranked evidence. Each group's selection excludes questions already allocated to the other group. Where a player has no recorded weak topic in scope, their five use the selected live pool and the fallback is disclosed. If a recorded weak-topic pool cannot provide the required distinct questions, acceptance fails clearly; scope is not silently broadened. The recipient can reject, and the pending reservation expires on its original deadline.

Each participant can progress independently through the identical Practice questions. Live updates show the other participant's score/progress, and restored sessions mask unanswered solutions. When enabled, each question has a server-enforced 60-second clock, started once through an authenticated endpoint; re-opening it cannot reset the start time. The server replaces late answers with TIMEOUT and records authoritative elapsed time, ignoring the client's claimed response time. When the timer is off, timeouts cannot be submitted to skip/farm a match. Completed-but-waiting users can return to Friends and reopen the duel. Failed clock initialization has an explicit retry state.

Both sessions must complete before the duel completes. Completion awards exactly 10 XP to each participant, once, inside the same transaction as terminal match state, using the centralized XP service and distinct idempotency keys. Ordinary per-question Practice and Ranked rewards are suppressed for friendly sessions. Abandonment, rejection, cancellation, expiry and incomplete matches award zero. XP progress-row locks also prevent friendly awards from overwriting concurrent ordinary awards. There are no coin/rating rewards. Friendly answers still contribute to ordinary Practice learning statistics and answer-based milestones. Untimed friendly answers are excluded from Home's timed-answer averages.

The winner has more correct answers. Equal scores are draws when the timer is off; with the timer on, lower server-recorded total answer time breaks a tie. Rewards remain 10 XP each regardless of winner. Friendly duels do not count as Ranked wins.

## Interfaces and validation

Authenticated `/api/v1/social` APIs provide friends, name search, public profiles, friend invite/respond/remove, inbox, duel create/get/respond/leave. Inputs, IDs, pagination and recipient roles are validated; social request bodies are bounded. `/ws/social` authenticates by an initial token frame, rechecks token validity on heartbeats and fans out account-scoped invalidation events. The app fetches authoritative state after those events. The new Practice question-start endpoint is owned by the session's user.

Validation includes backend builds, Prisma validation, existing Practice/Home regressions, social permission/selection/expiry/reward tests, a modeled XP-concurrency test, Flutter search/profile/invite and countdown tests, Practice snapshots and Android debug compilation. The tests do not run against a real database or Redis. Multi-replica load, actual row-lock behavior/deadlocks, query plans, proxy upgrades, process-restart recovery and signed-device Firebase/OAuth flows still require an authorized staging environment with the real infrastructure. No claim of proven million-user capacity is made without those measurements.
